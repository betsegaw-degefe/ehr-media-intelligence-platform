# EHR Media Intelligence Platform

Ingest messy, heterogeneous EHR records → clean and normalize them → map to **HL7 FHIR R4** → generate
**AI clinical summaries** with Claude → **semantic search** through a FastAPI endpoint and a Tailwind UI.

> All data in this repository is **synthetic** and generated by `scripts/generate_data.py`. No real patient data is used.

```
data/raw/  ──►  ingestion  ──►  FHIR mapper  ──►  validator  ──►  SQLite (bundles, resources, audit)
JSON · CSV · TXT   clean + audit   Bundle/patient   report.md          │
                                                                       ├──►  Claude summaries (cached by patient + content hash)
                                                                       └──►  MiniLM embeddings ──► ChromaDB ──► POST /search ──► Tailwind UI
```

## Quick start

Requires Python 3.11+ (developed on 3.12).

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python scripts/generate_data.py          # optional: data/raw is already committed
export ANTHROPIC_API_KEY=sk-ant-...      # optional: without it, summaries use the rule-based fallback
python scripts/run_pipeline.py           # ingest → FHIR → validate → store → summarize → index

uvicorn backend.api.main:app --reload    # API + UI on http://localhost:8000
pytest                                   # all tests
```

Open **http://localhost:8000** for the UI and **http://localhost:8000/docs** for the interactive API docs.

`run_pipeline.py` options: `--summarizer {auto,claude,rules}` (`auto` uses Claude when credentials exist),
`--skip-summaries`, `--skip-index`. Re-running is cheap: unchanged patients are cache hits and make no API calls.

### Pipeline outputs (`data/output/`, git-ignored)

| File | Contents |
|---|---|
| `clean_dataset.json` | Pydantic intermediate representation (patients, records, rejected records, stats) |

## API

| Method | Path | Description |
|---|---|---|
| `POST` | `/search?resource_type=&date_from=&date_to=` | Body `{"query": "...", "top_k": 5}`. Returns the top-k records ranked by cosine similarity, with patient name/MRN, date, type, snippet and AI-summary snippet. `resource_type` ∈ `DocumentReference`, `DiagnosticReport`, `AISummary`; dates are `YYYY-MM-DD`, inclusive. |
| `GET` | `/patients` | Patient list |
| `GET` | `/patients/{id}` | Demographics, latest AI summary, linked FHIR resources with their cleaning audit trail |
| `GET` | `/patients/{id}/bundle` | Raw FHIR Bundle JSON |
| `GET` | `/health` | Status and indexed-document count |

```bash
curl -s -X POST 'localhost:8000/search?resource_type=DiagnosticReport&date_from=2025-01-01' \
  -H 'Content-Type: application/json' -d '{"query": "lung nodule needing follow-up"}'
```

## Design decisions

### Task 1: Ingestion and cleaning
* **Loaders → common raw shape.** Each format has its own loader (`load_json`, `load_lab_csv`, `load_txt`) that maps
  field-name aliases (`mrn`/`patient_id`, `dob`/`birth_date`, nested vs flat patient blocks, `KEY: value` scan headers)
  onto one dict shape. Cleaning logic never needs to know the source format. Loading is tolerant: files are read
  with BOM-tolerant UTF-8, scan headers end at any `---`/`===` line (or the first non-header line), hidden files
  such as macOS `._*` forks are skipped, and a file or item that can't be parsed is reported as rejected instead of
  stopping the run.
* **Every cleaner returns `(value, [AuditEntry])`.** Each normalization, fill, merge, deduplication, conflict and
  rejection is recorded with old value, new value and reason. The audit log goes into the intermediate
  representation, the SQLite store and the UI (expand a resource in the patient drawer).
* **Dates.** Explicit formats are tried before `dateutil`, so parsing is deterministic. Slash dates are read as US
  `MM/DD/YYYY`, matching the convention of a US Epic export. A 2-digit year that produces a future DOB
  (`03/14/58` → 2058) is shifted back a century; a future DOB written with a 4-digit year is a data error and is
  dropped. Partial dates ("March 2019") are rejected rather than completed with today's day. A note with no header
  date takes the first date in its narrative.
* **Identity resolution is conservative.** MRNs are canonicalized to `MRN-000000`. A record with no MRN is attached
  to a patient only on an *exact* name + DOB match. If two MRNs share an exact name + DOB (a transposed-digit typo),
  they are merged into the MRN from the most authoritative source (EHR export > scanned notes > lab feed). Links
  are transitive (union-find), so a chain of typo'd MRNs still ends up as one patient. Other MRNs are kept as `old`
  identifiers. When demographics conflict under one MRN, the value from the most authoritative source wins (then
  the value seen in the most source files, so one lab CSV row per analyte can't outvote the EHR export) and the
  conflict is flagged. A record that can't be attributed to anyone is **rejected, not guessed**.
* **Deduplication** uses a whitespace- and case-insensitive fingerprint of (patient, date, type, text). Lab rows use
  (patient, date, test, value), and panels are grouped case-insensitively. Record ids become FHIR ids, so they
  are made FHIR-safe at ingestion (`[A-Za-z0-9-.]`, at most 60 characters) and then unique; a changed or reused
  id is audited. After that the record id and the FHIR id are the same everywhere.
* **Lab flags** map to HL7 interpretation codes and keep critical values distinct (`HH`, `LL`, `AA`). An
  unrecognized flag becomes `A` (abnormal, needs review) and is audited; it is never treated as normal.

### Task 2: FHIR R4
* **Resources:** `Patient`, `Encounter`, `DocumentReference` (notes, base64 `text/plain` attachment, LOINC note
  type), `DiagnosticReport` for imaging (category `RAD`, `conclusion` = impression) and labs (category `LAB`,
  `result[]` → one `Observation` per analyte with LOINC code, UCUM quantity, interpretation and reference range).
* **References:** every clinical resource has `subject → Patient/…`, and `encounter` / `context.encounter →
  Encounter/…`. Bundles are `type: collection` with absolute `fullUrl`s so relative references resolve.
  Encounters missing from the source are derived from patient + service date, so a note and the labs drawn the
  same day share an encounter.
* **Validation has three layers:** (1) `fhir.resources` models for structure, cardinality and datatypes; (2)
  required value-set bindings, which `fhir.resources` does not check (`gender: "F"` passes its validation); (3)
  integrity (unique resource ids, every reference resolves inside the Bundle, exactly one Patient). `fhir.resources` 8 ships
  R4B models. R4B is a technical correction of R4, and the elements used here are identical in both.

### Task 3: AI summaries
* **Structured output.** Claude returns JSON constrained by a JSON schema (`output_config.format`), so every summary
  has the same fields: chief concern, key diagnoses, recent media, flagged anomalies, narrative, confidence and
  rationale. The **disclaimer is added by code**, not generated, so it can't be dropped or reworded.
* **Accuracy rules in the system prompt:** use only stated facts, copy values exactly, say "Not documented" rather
  than guess, keep source terminology. The input is JSON (patient, records with id/kind/date/title/text, and
  data-quality notes), so quotes or angle brackets in source text can't break it and the model can cite record
  ids. Data-quality conflicts found during cleaning are passed in so they surface as anomalies.
* **Word limit:** the prompt asks for 170 words total, and the count covers every field the model writes,
  including the confidence rationale. If the summary is over 200, the pipeline makes one corrective retry that
  includes the previous output. If it's still over, it is shortened deterministically (narrative, older media,
  extra diagnoses, long items, then clinical anomalies; data-quality notes are always kept) and a warning is added.
* **Grounding checks after generation:** each diagnosis must share at least 60% of its content words with the
  source, every number in an anomaly must appear in the source as a whole value (so "4.7" doesn't match "14.7"),
  and every cited record id must exist. Failures are
  stored as `quality_warnings` and shown in the UI.
* **Cache:** SQLite, keyed by `patient_id + sha256(bundle entries)` plus a hash of the data-quality notes, the
  requested model and the prompt version. The hash ignores `Bundle.timestamp`, so only real input changes trigger
  a new API call. The UI shows the current-prompt summary for the current Bundle, preferring an LLM summary over
  the fallback. Each summary records the model that actually answered, which can differ from the one requested
  when the API falls back to another model.
* **Fallback:** with no API credentials, a deterministic extractive summarizer fills the same schema (labelled
  `rule-based-fallback`, confidence `low`). The platform runs end to end without a key, and tests make no network calls.

### Task 4: Semantic search
* `all-MiniLM-L6-v2` embeddings (normalized, CPU) stored in a persistent **ChromaDB** collection with cosine
  distance. Indexed: every DocumentReference and DiagnosticReport text, plus one `AISummary` document per patient.
* Resource type and date range are applied as Chroma metadata filters (`date_int` = `YYYYMMDD`) **before** ranking,
  so a filtered query still returns the best top-5 in range. Undated records never match a date filter. The
  relevance score is `1 − cosine distance`. The list of resource types lives in one place (`RESOURCE_TYPES`); the
  API's accepted values, its OpenAPI docs, `/resource-types` and the UI dropdown are built from it.
* **Rebuilding while the API runs.** Each pipeline run replaces the stored dataset (so patients merged away don't
  linger) and updates the Chroma collection in place: upsert the new documents, delete stale ones, then write a
  generation marker. Chroma keeps a per-process copy of the index, so the API reopens its client when the marker
  changes and serves the new index without a restart. The index uses the same summary the patient page shows
  (`SummaryCache.latest()`), and `--skip-summaries` keeps each patient's cached summary.
* **The API is read-only.** It opens SQLite with `mode=ro` and reads the summary cache without running DDL, so
  viewing a page can't change data or block the pipeline. CORS is off by default (the UI is served from the same
  origin); set `EHR_CORS_ORIGINS=http://host:port` to allow a frontend hosted on another origin.
* The embedding model is loaded once at app startup. A query then costs one forward pass plus an HNSW lookup:
  **about 5 ms per query over 66 indexed documents** on a laptop CPU, against a 2-second budget (asserted in
  `tests/test_search_api.py`).

### Task 5: Frontend
* One static page (`frontend/`) served by FastAPI: vanilla JS + Tailwind, using `fetch` with same-origin URLs only.
  The Tailwind CSS is compiled into `frontend/styles.css` and committed, so no third-party script runs on a page
  that shows patient data and nothing needs building to run the app. The page can't be pointed at another server
  from its URL, since a crafted link could otherwise send patient data elsewhere.
* Search runs on a 300 ms debounce, aborts in-flight requests, and shows skeleton loading, empty, no-results and
  error states.
* Result cards show name/MRN, date, a colour-coded resource-type badge, a relevance meter and the AI summary
  snippet. Clicking a card opens a drawer with the full summary, the disclaimer, quality warnings, and every linked
  FHIR resource (expandable text and cleaning audit trail).
* Accessibility: labelled controls, `role="search"`, `aria-live` status, `role="dialog"` with `aria-modal` and a
  focus trap. Keyboard: `/` focuses search, `↑`/`↓` move through results, `Enter` opens, `Esc` closes. Also a skip
  link, visible focus rings, and reduced-motion support.
* Stale responses are dropped: every search cancels the pending debounce and the in-flight request, and the patient
  drawer ignores a response for a patient other than the one now open (or one that arrives after it closed).
  Errors show what the server said; only a network failure suggests the API is down. Age is computed from
  calendar dates. Resource-type labels and colours come from one map in `app.js`.

#### Frontend CSS
`frontend/styles.css` is generated. After changing classes in `index.html` or `app.js`, rebuild it:

```bash
npx tailwindcss@3.4.16 -c frontend/tailwind.config.js -i frontend/tailwind.input.css -o frontend/styles.css --minify
```

`tests/test_frontend.py` fails if a class used in the page is missing from the compiled CSS.

## Testing

```bash
pytest
```

| File | Covers |
|---|---|
| `test_cleaning.py` | date formats, 2-digit years, gender/MRN/name normalization, duplicates, MRN conflict merge, MRN fill + rejection, demographic conflicts, inferred dates, lab panels, full synthetic dataset |
| `test_fhir.py` | all bundles valid, references and LOINC codes, merged MRN as `old` identifier, schema/binding/reference errors reported, SQLite round-trip, content hash |
| `test_summarizer.py` | JSON prompt, required fields + disclaimer, word-limit retry and enforcement, protected data-quality notes, grounding warnings, cache key and `latest()` selection, Claude response parsing and served model (mocked) |
| `test_search_api.py` | top-5 ranking, resource-type and date filters, 422 validation, patient detail endpoint, < 2 s latency with the real model |

API and search tests use a small deterministic hashing embedder, so they run offline. The latency test loads the real
MiniLM model and is skipped if the model can't be downloaded. `test_summary_cache.py` covers the read-only cache the
API uses. `test_frontend.py` checks the compiled CSS and, when Chrome or Chromium is installed, runs the real page
headless with a mocked `fetch` to test the drawer and search races, error messages, focus trap and age display.
